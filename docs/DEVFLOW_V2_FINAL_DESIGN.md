# DevFlow v2 최종 개발 설계서

- 문서 상태: 구현 기준 확정본
- 작성일: 2026-08-09
- 기준 코드: `main` (`5f66ddd`)
- 운영 보존점: `backup/main-before-report-v2-20260809`, `v1-before-report-v2-20260809`
- 1차 구현 범위: 영역/PL 구조, 일일보고 준비·확인·확정, 회의용 보고 보기, 회의 메모의 후속 태스크·일정 반영

## 1. 제품 목표

DevFlow v2의 첫 화면과 핵심 흐름은 사용자가 10초 안에 다음 세 가지를 알게 해야 한다.

1. 지금 프로젝트 전체 일정은 정상인지
2. 오늘 확인하거나 결정해야 할 위험은 무엇인지
3. 내 역할에서 지금 눌러야 할 다음 버튼은 무엇인지

단기간 프로젝트가 주 사용 대상이므로 **일 단위 운영과 일일보고를 주 단위 현황보다 우선**한다. PM에게 가장 먼저 보여 줄 것은 개발자의 세부 태스크 목록이 아니라 전체 일정, 영역별 진척, 지연·막힘, 오늘 결정할 사항이다.

## 2. 확정된 제품 원칙

### 2.1 기존 제품을 확장한다

- 정적 목업이나 별도 프로토타입으로 기존 앱을 교체하지 않는다.
- 기존 React/Vite, Express, PostgreSQL/Drizzle 구조를 유지한다.
- 기존 태스크, 일정, 문서, 회의록, 검색, AI, MCP, GitHub, PWA, 관리자 기능을 보존한다.
- 신규 기능은 프로젝트별 `daily_report_enabled` 기능 플래그가 켜진 경우에만 노출한다.

### 2.2 규모에 따라 역할 구조가 자연스럽게 달라진다

- 소규모 프로젝트: PM + 담당자
- 대규모 프로젝트: PM + 영역별 PL + 담당자
- 영역이 없으면 PL 관련 화면과 확인 절차를 표시하지 않는다.
- 프로젝트 소유자(owner)는 운영 역할과 별도의 안전 축으로 유지한다. 일반적으로 소유자와 PM이 같지만, 소유권 양도·영구 삭제 같은 파괴적 작업은 owner만 수행한다.

### 2.3 보고서는 여러 개를 취합하지 않는다

- 프로젝트당 회의일별 일일보고서 한 개를 공동으로 준비한다.
- 각 PL은 자기 영역 섹션만 확인하고 판단·사유·영향·요청을 보충한다.
- PM은 전체 일정·위험·의사결정을 확인한 뒤 보고서를 확정한다.
- 태스크에 이미 있는 수치와 목록을 PL이 다시 작성하지 않는다.

### 2.4 보고 마감은 근무 종료가 아니라 귀속 기준이다

- 기본 보고 마감은 전날 21:00이며 PM이 프로젝트 설정에서 변경할 수 있다.
- 마감 이후 개발을 금지하지 않는다.
- 마감 이후 완료·변경은 원칙적으로 다음 일일보고에 귀속한다.
- 당일 회의에서 반드시 알아야 할 긴급 위험은 `마감 이후 긴급 변경`으로 별도 표시할 수 있다.
- 개인별·영역별 퇴근 시간에 맞춰 보고서를 자동 생성하지 않는다.

### 2.5 보고서 확정은 회의 전에 한 번만 한다

- `회의 전`과 `회의 직전`을 별도 단계로 나누지 않는다.
- 회의 시작 전에 PL 확인 상태와 자동 집계 내용을 한 화면에서 최종 확인한다.
- PM이 `보고서 확정`을 누르면 회의에 보여 줄 버전이 고정된다.
- 회의 중에는 과거 실적을 조용히 수정하지 않는다.

### 2.6 회의 화면은 별도 회의 시스템이 아니다

- 명칭은 `회의용 보고 보기`로 통일한다.
- 확정된 같은 일일보고서를 발표하기 좋은 큰 글씨·간결한 레이아웃으로 보여 준다.
- QR/바코드 입장은 1차 범위가 아니다. 로그인한 PM/PL이 일반 URL로 연다.
- `회의 종료·보고서 확정` 단계는 만들지 않는다.

### 2.7 회의 결과는 미래 계획에 반영한다

- 회의 중 PM/PL은 변경·결정 메모를 남긴다.
- 회의 후 권한자가 메모를 검토해 태스크 생성, 태스크 수정, 일정 생성 후보로 반영한다.
- 회의가 끝난 시점에는 보고서의 완료 실적은 과거이므로, 합의 내용은 오늘 할 일 또는 다음 할 일에 반영한다.
- 확정 보고서의 사실 오류는 원본 덮어쓰기가 아니라 정정 사유가 있는 새 버전으로 처리한다.

## 3. 사용자와 권한 모델

### 3.1 두 개의 권한 축

| 축 | 값 | 목적 |
|---|---|---|
| 안전/소유권 역할 | owner, manager, member | 기존 호환, 소유권 양도, 삭제, 레거시 권한 |
| 운영 역할 | pm, pl, worker | v2 화면, 영역 범위, 일일보고 책임 |

기존 데이터의 초기 변환 규칙은 다음과 같다.

- owner → pm
- manager → pm (기존 manager는 프로젝트 전체 권한이었으므로 자동으로 PL로 축소하지 않는다)
- member → worker

PL은 PM이 특정 영역의 리드로 지정할 때 운영 역할을 `pl`로 변경한다. 마지막 담당 영역이 제거되더라도 자동 강등하지 않고 PM에게 정리 안내를 보여 준다.

### 3.2 역할별 핵심 행동

| 기능 | PM | PL | 담당자 |
|---|---:|---:|---:|
| 전체 일정·영역 현황 보기 | 가능 | 가능 | 필요한 작업 중심 |
| 공식 태스크 생성 | 전체 프로젝트 | 자기 영역 | 불가 |
| 작업 제안/티켓 생성 | 가능 | 가능 | 가능 |
| 프로젝트 설정 | 가능 | 불가 | 불가 |
| 자기 영역 관리 | 가능 | 가능 | 불가 |
| 영역 생성·삭제·PL 지정 | 가능 | 불가 | 불가 |
| 일일보고 준비 화면 | 가능 | 가능 | 노출 안 함 |
| 자기 영역 확인 | 대신 확인 가능 | 자기 영역 | 불가 |
| 보고서 확정·정정 | 가능 | 불가 | 불가 |
| 회의용 보고 보기 | 가능 | 가능 | 기본 노출 안 함 |
| 회의 메모 작성 | 가능 | 가능 | 불가 |
| 메모 후속 반영 | 전체 | 자기 영역 | 불가 |
| 공휴일·근무일 정책 변경 | 가능 | 불가 | 불가 |
| 개인 휴가 등록 | 본인 | 본인 | 본인 |

모든 권한은 UI 숨김뿐 아니라 서버에서 직접 URL/API 접근을 차단한다.

## 4. 정보 구조와 10초 이해 설계

### 4.1 프로젝트 기본 진입 화면

프로젝트 진입 시 역할에 따라 첫 행동을 다르게 안내한다.

- PM: `전체 일정과 위험 확인` → 요약 카드, 영역 상태, 다음 회의 보고 준비 버튼
- PL: `내 영역 확인` → 자기 영역 카드 강조, 확인이 필요한 막힘과 보고 코멘트
- 담당자: `내 작업 계속하기` → 오늘 담당 태스크, 마감 임박, 막힘 등록

프로젝트 공용 메뉴는 기존 메뉴를 보존하면서 다음과 같이 정리한다.

- 태스크·일정
- 일일보고 (기능 플래그가 켜지고 PM/PL일 때만)
- 문서
- 회의록
- 프리뷰
- 팀원

관리자 메뉴와 개인 설정은 기존 전역 메뉴에 남긴다. 프로젝트 설정은 PM에게만 명확한 버튼으로 제공하고, PL에게는 `내 영역 관리`만 제공한다.

### 4.2 일일보고 화면의 첫 문장

개발자 관점의 `완료 태스크 수`가 아니라 다음 문장 구조를 우선한다.

> 전체 일정은 [정상/주의/위험]이며, 오늘 [N]개 결정을 확인해야 합니다.

근거로 전체 진척, 일정 편차, 영역별 상태, 막힘, PL 확인 상태를 바로 아래에 보여 준다.

## 5. 일일보고 운영 흐름

### 5.1 기준 시각

- 회의 시각 기본값: 09:30
- 보고 마감 기본값: 전날 21:00
- 시간대 기본값: Asia/Seoul
- 보고일 D의 자동 집계 구간: D-2 21:00 초과 ~ D-1 21:00 이하
- 첫 보고서에는 이전 확정본이 없으므로 프로젝트 시작일 또는 전날 00:00을 시작점으로 사용한다.

마감 시각에 보고서 레코드를 자동 생성하지 않는다. 사용자가 보고 준비 화면을 처음 열 때 해당 날짜의 초안을 생성한다. 자동 집계는 고정된 마감 구간을 사용하므로 늦게 화면을 열어도 같은 결과를 만든다.

### 5.2 준비 단계

1. PM 또는 PL이 `일일보고`를 연다.
2. 시스템이 해당 회의일의 초안이 없으면 자동 집계 스냅샷을 만든다.
3. PL은 자기 영역의 완료·진행·막힘을 확인한다.
4. 자동 데이터가 맞으면 `영역 확인`, 설명이 필요하면 판단·사유·영향·요청을 입력한 뒤 확인한다.
5. PM은 확인하지 않은 PL을 알림하거나, 현재 데이터로 진행하거나, 직접 대신 확인할 수 있다.
6. PM은 전체 상태, 전체 요약, 오늘 결정사항을 입력하고 `보고서 확정`을 누른다.

PL 미확인은 경고이지 PM을 퇴근하지 못하게 만드는 강제 차단이 아니다. 대신 확인할 때는 누가 대신 확인했는지 감사 기록을 남긴다.

### 5.3 회의 단계

1. PM/PL이 `회의용 보고 보기`를 연다.
2. 확정 보고서의 전체 일정, 영역별 상태, 완료, 막힘, 오늘 계획, 결정 필요사항을 순서대로 보고한다.
3. 변경 합의가 생기면 화면 하단의 `회의 메모`에 기록한다.
4. 보고서 자체는 변경하지 않는다.

### 5.4 회의 후 단계

1. `후속 반영 대기` 목록에서 회의 메모를 검토한다.
2. 태스크 생성, 태스크 수정, 일정 생성, 단순 기록 중 하나를 선택한다.
3. 적용 전에 대상·제목·담당자·일정·영역을 다시 확인한다.
4. 적용 결과는 원 메모와 상호 링크하고 활동 로그에 남긴다.

## 6. 자동 집계 정의

### 6.1 집계 항목

- 완료: `completed_at`이 보고 구간에 포함되는 태스크
- 진행: 마감 시점 기준 `in_progress`
- 막힘: 마감 시점 기준 `blocked`
- 예정: 보고일에 `scheduled_date`가 잡힌 미완료 태스크
- 지연: 마감일이 지났고 완료되지 않은 태스크
- 결정 필요: PL/PM이 직접 표시한 요청 또는 막힘 중 PM 판단이 필요한 항목
- 마감 이후 변경: 보고 마감 후 상태·일정·담당·내용이 변경된 항목

### 6.2 마감 시점 상태 처리

기존 태스크 표는 현재 상태만 저장하므로 다음 순서로 최대한 정확하게 마감 시점을 재구성한다.

1. `completed_at <= cutoff`이면 완료로 본다.
2. 현재 태스크 `updated_at <= cutoff`이면 현재 상태를 사용한다.
3. 마감 이후 변경된 태스크는 활동 로그의 마감 이전 마지막 상태 변경을 사용한다.
4. 복원할 수 없는 오래된 데이터는 현재 상태를 임의로 과거 상태로 간주하지 않고 `확인 필요`로 표시한다.
5. v2 이후 상태 변경 활동에는 `from_status`, `to_status`를 기록해 재현성을 높인다.

초안 생성 시 집계 결과를 JSON 스냅샷으로 저장한다. 수동 새로고침은 초안에서만 가능하며 PL/PM 수동 메모는 보존한다. 확정 후에는 원 스냅샷을 바꾸지 않는다.

### 6.3 영역 없는 태스크

- `미분류` 영역으로 집계한다.
- 대규모 프로젝트에서 미분류가 존재하면 PM에게 정리 경고를 표시한다.
- 소규모 프로젝트에서는 영역을 만들지 않아도 전체 프로젝트 단일 섹션으로 자연스럽게 보인다.

## 7. 보고서 내용과 상태

### 7.1 보고서 구성

1. 전체 일정 상태: 정상/주의/위험
2. 핵심 한 문장
3. 전체 진척과 일정 편차
4. 영역별 현황과 PL 확인 상태
5. 구간 내 완료
6. 진행 중·지연
7. 막힘과 필요한 지원
8. 보고일의 계획
9. 오늘 결정할 사항
10. 마감 이후 긴급 변경
11. 작성·대신 확인·확정 이력

### 7.2 상태 모델

- `draft`: 자동 집계와 수동 코멘트를 수정할 수 있음
- `confirmed`: PM이 회의 전에 확정한 불변 버전
- `superseded`: 사실 오류 정정으로 새 버전이 만들어진 이전 버전

별도의 `회의 중`, `회의 종료`, `보고서 재확정` 상태는 만들지 않는다.

### 7.3 정정

- PM만 확정본을 정정할 수 있다.
- 정정 사유가 필수다.
- 기존 버전은 남고 새 버전 번호가 생성된다.
- 회의에서 계획이 바뀐 것은 정정이 아니라 후속 태스크·일정 변경이다.

## 8. 영역과 태스크 운영

### 8.1 영역

- PM이 영역을 만들고 이름, 설명, 색상, 정렬 순서, PL을 지정한다.
- PL은 자기 영역의 설명과 표시 순서를 수정할 수 있으나 영역 삭제·PL 교체는 할 수 없다.
- 영역은 별도 DevFlow 프로젝트가 아니다. 문서·일정·보고를 분리하지 않고 하나의 프로젝트 안에서 관리한다.
- 태스크마다 `area_id`를 선택적으로 가진다.

### 8.2 태스크 생성

- PM: 어느 영역이든 공식 태스크 생성
- PL: 자기 영역에 공식 태스크 생성
- 담당자: 공식 태스크가 아니라 티켓/작업 제안 생성
- PL이 직접 URL이나 MCP로 다른 영역에 공식 태스크를 만들거나 수정하지 못하게 서버에서 검사한다.

기존 owner/manager/member 동작은 기능 플래그가 꺼진 프로젝트에서 그대로 유지한다. 플래그가 켜진 프로젝트부터 운영 역할과 영역 범위를 적용한다.

## 9. 휴가·공휴일·장기 휴무

### 9.1 개인 일정

- 개인 휴가·부재는 기존 개인 일정에 등록한다.
- 본인은 상세 사유를 볼 수 있다.
- PM/PL은 `종일 부재/부분 부재`, 기간, 태스크 영향만 보고 민감한 상세 사유는 보지 않는다.
- 해당 날짜에 배정된 태스크가 있으면 담당자와 PM/PL에게 일정 충돌을 경고한다.

### 9.2 공휴일과 장기 휴무

- 국가 공휴일 또는 조직 공통 휴무는 프로젝트 캘린더에 범위 일정으로 표시한다.
- `공휴일·근무일 설정`은 PM만 변경한다.
- PL과 담당자가 버튼을 눌러 프로젝트 설정 전체를 볼 수 없게 별도 읽기 요약만 제공한다.
- 장기 휴무가 마감일·예정일과 겹치면 기간 전체를 검사해 위험을 표시한다.
- `추석 연휴 보기`처럼 특정 연휴에 종속된 버튼을 만들지 않고 `휴일·휴무 전체 보기`와 현재 일정에 가까운 휴무 요약을 제공한다.

이 항목은 일일보고의 가용 인원·일정 위험 입력으로 연결하되, 1차 구현에서는 기존 일정 데이터를 읽어 경고하는 수준으로 시작한다.

## 10. 문서·첨부·검색·KoRDoc

### 10.1 업로드 구분

- 공식 문서/회의록: 문서·회의록 영역에 업로드하고 파싱·색인한다.
- 태스크 댓글 첨부: 해당 작업의 증빙 파일로 취급한다.
- 댓글 첨부를 자동으로 공식 문서로 승격하거나 전체 태스크와 자동 연결하지 않는다.
- 필요하면 PM/PL이 `공식 문서로 등록`을 선택한다.

### 10.2 KoRDoc 연동 원칙

- 사용자 검증이 끝난 KoRDoc을 파싱 계층으로 사용한다.
- HWP/HWPX/PDF/DOCX/XLS/XLSX/이미지 OCR 결과를 공통 청크 모델로 변환한다.
- 파싱 결과를 검색 색인하고 관련 태스크 후보를 만든다.
- 자동 매칭은 제안일 뿐이며 PM/PL이 승인해야 실제 연결한다.
- 기존 `source_page_id` 단위 매칭을 프로젝트 전체 문서-태스크 후보 검색으로 확장한다.

### 10.3 검색 범위

- 기본 검색: 태스크 키, 제목, 설명, 체크리스트
- 프로젝트 검색: 기본 검색 + 댓글, 가이드, 회의록, 문서 본문, 첨부 파싱 텍스트
- 전역 AI 검색: 권한이 있는 프로젝트의 위 항목 + 스킬
- 첨부 원문과 개인 기록은 기존 권한 경계를 유지한다.

KoRDoc 전체 연동은 일일보고 1차 배포 뒤의 별도 단계다. 이번 스키마와 UI가 이를 막지 않도록 영역·문서 연결점을 보존한다.

## 11. MCP와 자동화

- 기존 OAuth/PAT와 기존 MCP 도구를 삭제하거나 이름 변경하지 않는다.
- 신규 프로젝트·태스크 쓰기 도구에는 운영 역할과 영역 범위 검사를 적용한다.
- 일일보고용 도구를 추가한다.
  - `get_daily_report`
  - `update_daily_report_area_note`
  - `confirm_daily_report_area`
  - `add_daily_report_meeting_memo`
- PM 확정과 메모의 실제 태스크·일정 반영은 실수 비용이 크므로 MCP에서도 명시적 확인 인자가 필요하다.
- MCP가 만든 변경은 `via: mcp`로 활동 로그에 남긴다.

## 12. 데이터 모델

### 12.1 기존 표 확장

`projects`

- `daily_report_enabled boolean not null default false`
- `report_cutoff_hour integer not null default 21` (0~23)
- `report_meeting_time text not null default '09:30'`
- `timezone text not null default 'Asia/Seoul'`

`project_members`

- `operational_role text not null default 'worker'` (`pm|pl|worker`)

`tasks`

- `area_id integer null references project_areas(id) on delete set null`

### 12.2 신규 표

`project_areas`

- id, project_id, name, description, color, sort_order
- lead_user_id (프로젝트 멤버만 가능)
- created_by, created_at, updated_at
- 프로젝트 내 영역 이름 unique

`daily_reports`

- id, project_id, report_date
- version, status
- period_start, cutoff_at
- snapshot jsonb
- overall_status (`normal|warning|risk`)
- headline, pm_summary, decisions
- correction_reason
- created_by, confirmed_by, confirmed_at, created_at, updated_at
- `(project_id, report_date, version)` unique
- 날짜별 활성 초안은 서비스 로직과 트랜잭션으로 한 개만 유지

`daily_report_area_reviews`

- id, report_id, area_id nullable (`null`은 소규모 전체/미분류)
- reviewer_id, confirmed_by, confirmed_at, confirmed_for_id
- status (`pending|confirmed`)
- judgment (`normal|warning|risk`)
- note, impact, request
- `(report_id, area_id)` unique (null 영역은 별도 보정 인덱스/서비스 규칙)

`daily_report_memos`

- id, report_id, area_id nullable, author_id
- body, action_type (`task_create|task_update|event_create|note`)
- status (`pending|applied|rejected`)
- action_payload jsonb
- target_task_id, target_event_id
- reviewed_by, applied_at, created_at, updated_at

### 12.3 삭제 규칙

- 프로젝트 삭제 시 영역·보고서·메모도 기존 프로젝트와 함께 cascade 한다.
- 영역 삭제 시 태스크의 `area_id`는 null로 바꾸고, 확정 보고서 snapshot은 그대로 유지한다.
- 보고서에 포함된 사용자 표시명·영역명은 snapshot에도 보존해 이후 멤버/영역 변경으로 과거 보고가 깨지지 않게 한다.

## 14. 클라이언트 화면

### 14.1 경로

- `/projects/:id/reports` — 날짜 목록과 최신 보고 준비
- `/projects/:id/reports/:reportId` — 준비/미리보기 공용 화면
- `/projects/:id/reports/:reportId/present` — 회의용 보고 보기
- `/projects/:id/reports/:reportId/follow-ups` — 회의 후속 반영

### 14.2 보고 준비 화면

- 상단: 보고 날짜, 귀속 구간, 마감 시각, 확정 상태
- 첫 카드: 전체 일정 상태와 핵심 한 문장
- 영역 스트립: 상태, 진척, 완료/막힘, PL, 확인 상태
- 본문: 완료/진행/막힘/오늘 계획/결정사항
- 우측 또는 하단 고정 행동:
  - PL: `내 영역 확인`
  - PM: `보고서 확정`
- 누락 PL이 있어도 PM에게 세 가지 선택을 제공한다.
  - 알림 보내기
  - 현재 데이터로 진행
  - 대신 확인

### 14.3 회의용 보고 보기

- 본문 16px 이상, 제목 24px 이상
- 화면 공유에서 읽히도록 대비와 행간 확보
- 편집 입력은 숨기고 회의 메모 입력만 제공
- `보고서 미리보기`와 별도 보고서를 만들지 않는다. 준비 화면의 읽기 모드와 같은 데이터를 사용한다.
- 인쇄는 브라우저 인쇄 CSS로 PDF 저장을 지원한다. Markdown 내보내기는 후속 기능으로 둔다.

## 15. 보안과 감사

- 세션 mutating 요청의 기존 CSRF 헤더 규칙을 유지한다.
- 모든 projectId/reportId/areaId 관계를 서버에서 교차 검증한다.
- PL 범위는 `lead_user_id`와 `task.area_id`로 서버 검증한다.
- 확정 보고서는 일반 PATCH로 수정할 수 없다.
- 대리 확인, 확정, 정정, 메모 적용은 활동 로그에 사용자·시각·대상·변경 전후를 남긴다.
- 개인 일정의 상세 사유는 보고 snapshot에 저장하지 않는다.
- Bearer/MCP 토큰도 REST와 같은 역할·영역 검사를 통과해야 한다.

## 16. 마이그레이션과 운영 호환

- 기존 단일 `0000_init.sql`의 idempotent 규칙을 유지해 `ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`로 확장한다.
- 기존 레코드를 삭제하거나 enum 타입으로 강제 변환하지 않는다.
- 기존 owner/manager를 pm으로, member를 worker로 한 번만 backfill한다.
- 신규 기능 기본값은 꺼짐이다.
- 운영 DB 마이그레이션 전 백업을 확보한다.
- 배포 후 테스트 프로젝트 하나에서만 기능을 켠다.
- 롤백은 `git reset --force`가 아니라 `git revert`를 사용한다. 추가된 DB 컬럼/표는 즉시 삭제하지 않아 이전 코드가 무시하도록 둔다.

## 18. 테스트 시나리오

### 권한

- worker가 보고 목록/API/직접 URL에 접근하면 403
- PL이 타 영역 보고 코멘트·확인·태스크 변경을 시도하면 403
- PL이 프로젝트 전체 설정을 열면 403
- PM은 누락 PL을 대신 확인할 수 있고 감사 로그가 남음
- owner 안전 역할과 운영 PM 역할이 분리되어도 소유권 양도가 유지됨

### 시간 경계

- 20:59:59 완료는 다음 09:30 보고에 포함
- 21:00:01 완료는 그다음 보고에 포함
- 프로젝트 cutoff를 바꾸면 새 초안부터 적용
- 서버가 마감 시각에 꺼져 있어도 준비 시점에 고정 구간으로 초안 생성

### 불변성

- draft는 새로고침 가능하고 수동 메모 보존
- confirmed는 PATCH/refresh 거부
- 정정 시 이전 버전 보존, 사유 필수
- 영역 삭제 후에도 과거 snapshot의 영역명 유지

### 회의 후속

- 메모는 작성 즉시 태스크를 변경하지 않음
- 적용 전 미리보기와 명시적 승인 필요
- 같은 메모 두 번 적용 불가
- PL은 자기 영역 후속만 적용
- 적용 결과가 원 메모와 활동 로그에 연결

### 회귀

- 기존 98개 테스트 전부 통과
- 태스크 리스트/칸반/캘린더/타임라인, 문서, 회의록, 일정, 검색, AI, MCP, 관리자, 초대 기능 정상
